# 实机踩坑记录

这些不是设想，是在真机上一遍遍失败后改出来的。换设备、换摆位、换输入法时，先把这份清单过一遍。

## 运动与时序

| 现象 | 原因 | 现在的处理 |
|---|---|---|
| 点一下弹出图标菜单，像长按 | 下压太慢，Z 行程 7 mm 用 `F300` 要 1.4 秒 | 普通点按 `z_down_feed: 1200`，且受固件 `$112`（Z 最大速率）限制；点完只保留 `dwell_ms` 就松开 |
| 滑动也变成长按，页面不动 | 先等完整的下压，再开始 XY，起点被按住约 1 秒 | 先发一段 `G1 X… Y… Z… F900` 让 Z 与 XY 同时启动，起步横移 ≤10 mm，紧接着继续拖，最后才抬笔 |
| 抬笔时听到打齿 | 手动发 Z 上行 | 不发上行。弹簧回弹后只用 `G92` 重设逻辑 Z 坐标 |
| 屏幕下沿点不亮，上沿反而太重 | 手机底部高度不平 | `z_contact_map` 按坐标记录局部接触深度，一次只调一个点 |
| 服务重启后所有动作被拒 | 原点只在内存里，重启即失效 | 先 `status` 看 `origin_valid`，人工对中心后 `set-zero` |
| 移动很慢 | 每步都重新打开串口、等满读取 | 串口常驻；按已到达字节读；释放后不重复等 0.35 s |

## 坐标与标定

- 摄像头照片像素 ≠ 触屏坐标。必须用标定得到的仿射矩阵。
- 采样页视口尺寸变化（全屏切换、浏览器缩放）会让旧矩阵失效；采样过程中视口变了，当前点应直接拒收。
- 屏幕边缘没有直接采样，靠外推；别把目标点到贴边 12 px 以内。
- 摄像头分辨率一变（例如 720×1280 → 1440×2560），透视矫正参数全部作废，必须重标。

## 手机界面

- **同名图标**：桌面上可能有两个都叫「微信」的图标，打开后要核对标题/聊天列表，不能只看图标。
- **全局搜索**：聊天页顶部放大镜是全局搜索，搜出来的是网页/商品。联系人要从通讯录或当前聊天列表进。
- **负一屏**：从屏幕左边缘往右滑会打开负一屏，不是翻桌面。翻页从屏幕中部开始。
- **桌面末页**：已经在最后一页时，同方向再滑不会换页；先换方向，别误判成没收到触摸。
- **键盘布局**：九宫格拼音和 QWERTY 的键位完全不同，按 QWERTY 坐标点九宫格会全错。每种布局单独标。
- **键盘收起**：发送键会跑到最底部，之前记录的键盘态坐标失效；保持键盘打开再发。
- **发送键很敏感**：不同机型/缩放下差几个像素就点不中，必须以「新时间戳消息出现 + 输入框清空」确认，不能只看 API ok，也不能反复盲点。

## 流程设计

- API 返回 `ok` 只代表运动完成。**业务成功只能靠新画面判断**。
- 连续输入文字用 `/api/tap-sequence`：整串先校验，失败就一个键都不点；成功后只停车一次。
- 发送、发布、删除、付款这类外发动作必须显式授权（`--approve-send` 或任务描述里写明），执行前记录 `action_in_progress`，中断后不允许自动重发。
- 固定流程只适合页面稳定的场景。新页面、布局变化时先用 `ai-task` 跑通并逐屏核对，再把步骤固化成 YAML。
- 首次接触某台设备时，先做抬笔移动和拍照测速，再跑完整流程；不要一上来就发消息。

## 实测参考（一台具体设备，仅作量级参考）

- 首次打开摄像头约 1.9 s；之后每请求一张新帧约 82–85 ms（本机帧龄 3–5 ms，不含手机到电脑的传输延迟）。
- 抬笔移动 10 mm 约 270 ms（改造前约 1.13 s）。
- 普通点按端到端约 2.2 s；远距离主页键约 3.9 s。

换机器、换行程、换速度配置后这些数字都会变，不要当成承诺。
